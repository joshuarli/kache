---
title: Command reference
description: Every top-level Kache command, its purpose, and common flags
---

Run `kache <command> --help` for the exact syntax in your installed version.

Human output uses section headings, aligned values and status colors. Colors are disabled when stdout is redirected, `NO_COLOR` is nonempty, or `TERM=dumb`. Long summary notes wrap to the terminal width; paths remain complete.

`--json` emits one versioned JSON document for `init`, `list`, `stats`, `report`, `clean`, `gc`, `doctor`, `explain`, and `daemon status`. It works before or after the command. Use `init --json --check` to preview setup, or `init --json --yes` to apply it without prompts. `init --shims` has no JSON form. `doctor --json` only reports; combined with `--fix`, `--purge-sccache`, `--verify`, `--checksums` or `--repair` it exits with an error.

`clean --dry-run --json` previews cache removal. `clean --json` and `clean --crate <name> --json` are refused without `--dry-run`. `clean --cache --stale <age> --json` and `clean --cache --stale-schema --json` evict immediately and print GC fields.

Every document includes `schema_version`, `command`, and `success`. Successful commands keep their existing fields and may include `next`, an array of suggested commands with `argv` and `why`. Failures include `error.code`, `error.message`, and `error.causes`, and exit nonzero: 2 for argument errors, 1 for command failures. Progress and warnings go to stderr. `success` means the command completed; diagnostic findings remain in the command's fields, such as `issues` for doctor.

The envelope is documented in [`cli.schema.json`](https://github.com/kunobi-ninja/kache/blob/main/docs/commands/cli.schema.json). Byte counts and durations stay numeric rather than formatted strings. `stats --json` includes count and compile-time hit rates, time saved, wrapper timings, daemon identity, and storage diagnostics. `stats --full --json` and `report --json` add the envelope fields to the full report. Explicit `--format json` keeps the standalone report schema. With `--json --output`, stdout contains a file receipt. `--json --help` describes the whole visible command tree and its flags, whichever command it follows; hidden commands and flags are left out. `--json --version` reports the version.

| Command | Purpose |
| --- | --- |
| `init` | Configure Cargo, optional C/C++ shims, test pacing, and the daemon service |
| `doctor` | Diagnose setup and store integrity |
| `config` | Inspect or change configuration |
| `stats` | Hit rate, time saved and cache size; `--full` for the full build report. Alias: `status` |
| `clean` | Remove cache entries |
| `explain` | Explain why a crate missed the cache |
| `list` | Inspect local entries |
| `daemon` | Inspect and manage the background daemon |
| `completions` | Generate shell completion scripts |

These are for CI, scripts and integrations, and are not listed by `kache --help`:

| Command | Purpose |
| --- | --- |
| `cargo` | Run Cargo with Kache as its Rust compiler wrapper |
| `telemetry` | Write cache counters as OTLP JSON for Kartero (`write`) |
| `report` | Same report as `kache stats --full`, kept for scripts |
| `gc`, `purge` | Evict cache entries by policy or remove them explicitly |
| `install-shims` | What `kache init --shims` does, kept for scripts |
| `why-miss` | The earlier name of `kache explain` |

## `kache cargo`

```bash
kache cargo -- build
kache cargo -- check --workspace
```

Pass Cargo arguments after `--`. Kache sets `RUSTC_WRAPPER` to its frontend and forwards the arguments to Cargo.

## `kache list`

```bash
kache list
kache list serde
kache list --sort size --no-pager
```

Sort values are `name`, `size`, `hits`, and `age`.

Interactive output uses `KACHE_PAGER`, then `PAGER`, then a platform default. `--no-pager` writes directly.

## `kache clean`

### The cache

```bash
kache clean --cache --dry-run
kache clean --cache
```

`kache clean` empties the main store; volume shards keep their entries. It asks first, and without a terminal it removes nothing unless `--yes` is set. It also deletes the index files kept after index corruption, and says how many before it asks.

You rarely need `--cache`: the daemon evicts entries on its own to keep the cache under `cache.local_max_size`, starting with stale, rarely hit entries that free the most space. For scripts, `--cache --stale 30d` evicts older entries and `--cache --stale-schema` removes entries created with old or unrecorded key schemas without asking. `--crate serde` removes one crate's entries after asking.

Eviction affects only the local store. It also sweeps each `[cache.volumes]` shard against that shard's own budget; see [Configuration: Volume shards](/docs/getting-started/configuration#volume-shards). `--stale-schema` sweeps only the main store.

Eviction reports store bytes removed separately from bytes reclaimed on disk. It keeps an entry when its last store blob is still cloned into a build output, because unlinking that blob would free no disk and destroy a usable hit. This can leave the registered store size above `cache.local_max_size`; remove stale targets to reclaim the blocks. A size sweep leaves those held bytes out of its budget instead of evicting other entries to make up for them.

Set `cache.gc_evict_shared = true` or `KACHE_GC_EVICT_SHARED=1` to restore the older namespace-first policy. That lowers the registered store size but does not reclaim blocks retained by target directories, and the discarded entry becomes a future miss. See [Configuration: GC and shared build outputs](/docs/getting-started/configuration#gc-and-shared-build-outputs).

Eviction flushes any entries still pending durability before it judges them (see [Architecture](/docs/how-it-works/architecture)).

`kache gc` evicts by the size and age limits now, as the daemon does. `kache purge` removes cache entries. They are hidden from `--help`.

GC also recovers rebuild costs for older cache entries over successive runs. A pass that recovers no positive costs may still leave pending work. Metadata that cannot be read is retried later.

## `kache init`

```bash
kache init
kache init --check
kache init --no-service
kache init --no-shell
kache init --yes
```

`--check` (also `--dry-run` or `-n`) lists the changes init would make without writing. It ends with the `kache init` command and flags that apply them, or says there is nothing to change. With `--json`, each entry in `steps` says what init does to one component: `configure`, `update`, `keep`, or why it cannot (`unsupported`, `unavailable`, `manual`). A `backup` step names each existing file init would copy before editing it. After a real run, `steps` says what was done: a declined step is `skip`, and one that did not succeed is `failed`. `--no-service` skips login-service installation. `--no-shell` leaves shell startup files alone: no shim directory on `PATH` (C/C++ compilers and `cargo`). Cargo's native dependencies are still configured through `[env]`. When the service cannot be installed, such as on a Linux host without a systemd user session, init reports why and starts the daemon directly.

Init shows a setup plan and asks once before applying it. Replacing another Cargo wrapper requires a separate confirmation. `--yes` accepts both. If stdin has no answers, init exits 1 before changing files or services and prints the same command with `--yes`. Init backs up a file before it edits it, but not a file the same run created. Besides `rustc-wrapper`, init adds `HOST_CC` / `HOST_CXX` / `CC_KNOWN_WRAPPER_CUSTOM` under Cargo `[env]` when those keys are absent. It never sets `CC` or `CXX`.

On Unix, init also adds the C/C++ compiler shims to the shell startup files. `--no-shell` skips that edit.

### Compiler shims

```bash
kache init --shims
kache init --shims --from-path
kache init --shims --force
```

Unix only. `kache init` offers to create them; `kache init --shims` creates only them. It makes `cargo`, `cc`, `c++`, `gcc`, `g++`, `clang`, and `clang++` symlinks to Kache. The `cargo` link runs the real Cargo (`KACHE_REAL_CARGO`, else the next `cargo` on `PATH`) and forwards its arguments unchanged.

The farm is `~/.local/lib/kache/shims` unless a directory follows `--shims`, as in `kache init --shims /usr/lib/kache`. It also links each versioned C and C++ compiler on `PATH` (`clang-19`, `clang++-19`, `gcc-13`), matched by name without running it; `--canonical-only` leaves those out. The hidden `kache install-shims` does the same, for older scripts. `--from-path` also wraps every other compiler name on `PATH`, such as target-prefixed drivers. Put the directory before the real compilers in `PATH`. If the directory then holds only Kache links, Kache also writes a `.kache-shims` marker. When Kache looks for the real compiler, it skips everything in a marked directory. A directory that also holds other files, such as a real compiler, is left unmarked.

The links point at a path that survives upgrades when one reaches the running binary: Homebrew's `opt` link, a Nix profile, mise's `latest` alias, or a `kache` on `PATH` outside version directories. Without `--force`, existing entries are kept, except in a directory Kache created, marked, or filled only with Kache links. There a rerun replaces Kache links whose target is missing or not executable, and moves Kache links into a version directory to the upgrade-safe path. Other links are kept. See [C and C++](/docs/getting-started/c-cpp#upgrades).

## `kache doctor`

```bash
kache doctor
kache doctor --probe
kache doctor --fix
kache doctor --verify
kache doctor --checksums
kache doctor --repair
```

- `--fix` migrates from sccache: it stops a running sccache server, replaces `sccache` with `kache` in `$CARGO_HOME/config.toml`, and prints the lines to change in your shell startup files. It does not set up other missing pieces such as `rustc-wrapper` or the shims; run `kache init` for those.
- `--purge-sccache` also deletes the sccache cache directory (`~/Library/Caches/Mozilla.sccache` on macOS, `~/.cache/sccache` on Linux) and runs `cargo uninstall sccache` when sccache was installed with Cargo. It requires `--fix`.
- `--verify` checks entries, blobs, and metadata. It exits 1 while corrupted entries or index mismatches remain, so a scheduled job can gate on it. Orphan blobs do not count.
- `--probe` compiles a small Rust library, removes its output, then checks that the second invocation restores identical bytes without running the compiler. It uses an isolated temporary cache and configuration and removes its files afterwards. Each wrapped invocation has a 30-second deadline. It can also run with `--json`; findings appear in `checks` and `issues`.
- `--checksums` also hashes blob contents and implies `--verify`.
- `--repair` removes corrupted entries, reconciles the index with the entries on disk, reclaims orphan blobs, prunes stale C/C++ memos, input predictions and old file hashes, and compacts a large, sparse index when disk space allows. It implies `--verify`.

`--purge-sccache` and `--repair` delete data. Check what they will remove before running them.

Doctor reports issues and still exits 0; scripts read them from `kache doctor --json`. Only `--verify`, and the options that imply it, exit 1 for what they find.

Doctor checks cache-directory write access and read/write access to existing index, WAL and SHM files. On Unix it also shows this process's soft and hard open-file limits. Run it as the same user and in the same environment as the failing build.

Where volume information is available, doctor checks free space for the cache, Cargo outputs and temporary files, using existing ancestor directories for paths not created yet. The cache warning uses `cache.auto_recover_min_free_bytes`, with a minimum working reserve of 1 GiB even when automatic recovery is off. Cargo output and temporary volumes use the 1 GiB reserve.

Storage rows include the volume identity when reported. Unix rows show available and total inode counts; exhausted inodes are an issue even when bytes remain free. Unreported inode capacity stays unavailable. Distinct volume identities can share capacity through an APFS container, so their free-space figures are not independent. These checks do not remove anything.

When a daemon answers, doctor compares its reported configuration with this process's snapshot and names differences in store paths and other reported settings. New daemons also report their PID, effective user and open-file limits captured after startup raised the limit. Older daemons show an informational notice when those fields are unavailable. The temporary cache probe checks the local Rust pipeline separately from the configured store and project-specific flags.

If a build emitted a store-open warning in the last 24 hours, doctor reports that history even when the database opens now. The history is informational and depends on the warning marker remaining in the same temporary directory. To capture the full error, rerun the failing Cargo command with `KACHE_LOG_FILE=kache=debug,kache_store=debug` and inspect `kache.log` (see [diagnostic logs](/docs/daemon/lifecycle)).

Doctor reports where the running binary is installed ("Install path"), whether the C/C++ shims are active, broken, not first on `PATH` or not installed, and whether the login service runs a binary that no longer exists, is not executable, or is a different file from the running Kache. Run `kache daemon install` to fix the last one.

## `kache stats`

```bash
kache stats
kache stats --since 15m
kache stats --full
```

`kache stats` (alias `status`) groups its summary into Builds, Lifetime, Storage and Services. The Builds section shows local hit counts, duplicates and misses in its `Sources` row. `Cache` counts registered, deduplicated blob bytes. GC compares them with `Limit`, leaving out blobs that a `target/` directory still holds as a clone, because evicting those frees no disk; `On disk` shows that split, so `Cache` can stay above `Limit` with nothing left to evict. `Volume` shows the free and total space of the volume holding the cache, and whether [free-space recovery](/docs/getting-started/configuration#free-space-recovery) is on; JSON carries it as `volume` (`total_bytes`, `free_bytes`, `recovery_floor_bytes`, `below_floor`). `Dedup` shows logical entry bytes and the space saved by sharing blobs. `By time` weights hits by compile work, and `Miss time` shows the time spent on misses with its share of wrapper time. Index size and WAL size stay in the summary; rowid high-water marks appear under `--full` and in JSON. `--full` prints the full build report described below.

Below the window's rows, a section starting with `Since` shows totals since kache began counting: compile time avoided and the number of hits, bytes restored by reflink or hardlink against bytes copied, and store bytes GC removed, split into automatic runs (the daemon and the auto-GC worker) and `kache gc` runs you started. The event log rotates by size, so each rotation adds the events it drops to `savings.json` in the cache dir, and each GC run that frees bytes adds them there too. The totals are that file plus the events the log still holds, and volume shards add their own GC totals. The section is left out until something is counted. A crash between a rotation and its update of `savings.json` loses those events from the totals; nothing is ever counted twice. A corrupt `savings.json` is moved to `savings.json.corrupt` and counting starts over; one written by a newer kache is left alone. `kache stats --json` carries the same figures in a `lifetime` object (`since`, `hits`, `hit_compile_time_ms`, `zero_copy_bytes`, `copied_bytes`, `pruned_automatic_bytes`, `pruned_requested_bytes`).

`--since` accepts `s`, `m`, `h`, and `d` units (`90s`, `15m`, `2h`, `7d`). A bare number is hours. The default is `24h`. The counters and the `last ...` label both describe the requested window. A value that does not parse, or 0, is an argument error. A window reaches past the event log's size rotation: each rotation also keeps the lines it drops as a compressed segment in `events.jsonl.archive/` next to the log. Each rotation prunes the archive to 8 days and 512 MiB.

`--record` also appends one JSON line to `telemetry/sessions.jsonl` in the cache dir. The line holds the report's summary and timing breakdown, and the machine's load average, CPUs and index size at that moment. The root is stored as a hash. The runtime dir a CI job deletes on exit is where the report reads its events; this line is what survives on the machine. `KACHE_RECORD_SESSIONS=1` or `[cache] record_sessions = true` makes every report record the same way without the flag, and appends each GC run to `telemetry/gc-runs.jsonl`; it is off by default. With neither, the command writes nothing.

### The full report

```bash
kache stats --format text --since 24h
kache stats --format markdown --root "$PWD"
kache stats --full --root "$PWD" --format markdown
kache stats --format json --output report.json
kache stats --format trace --output trace.json
```

| Flag | Default | Values or purpose |
| --- | --- | --- |
| `--full` | off | The full report instead of the summary. `--format`, `--output`, `--top`, `--record`, and `--redact` imply it |
| `--format` | `text` | `json`, `trace` (also `perfetto`, `chrome-trace`), `markdown` (`md`), `github` (`gh`), `text`. Any other value is an argument error. `--json` gives `json`, and combining it with a format other than `json` or `text` is an error |
| `--since` | `24h` | Event window; same forms as `kache stats` (`15m`, `2h`, `7d`, bare hours) |
| `--root` | all roots | Only events from that build tree and the trees below it. Remote transfers are left out because the transfer log records no root. On `stats` it needs `--full` |
| `--output`, `-o` | stdout | Write to a file |
| `--top` | `10` | Number of ranked entries |
| `--redact` | off | Replace cache keys, roots, object keys, and object paths with `redacted` |

`trace`, `perfetto`, and `chrome-trace` select the same trace representation. `kache report` takes the same flags and prints the same report, for scripts written before `--full`. The JSON contract is documented by [`report.schema.json`](https://github.com/kunobi-ninja/kache/blob/main/docs/commands/report.schema.json).

Raw compiler events at schema 26 add `rebuilt_package`, `rebuilt_fingerprint`, `rebuilt_path` and `rebuilt_paths` when an actual successful compile produced outputs. Unknown package metadata is omitted. `rebuilt_fingerprint` is Kache's input cache key, not Cargo's on-disk freshness hash. Cache restores and Fresh Cargo artifacts do not report a rebuild. Tagged cleanup records report removed units separately from compiler `BuildEvent` records.

Every report format totals the wrapper's phases per crate: startup, key computation, lookup, scheduler wait, restore or store, and the unattributed remainder. Startup runs from process start to wrapper entry. Key computation splits out the rustc dep-info pre-pass by time and run count. Scheduler wait is the flight join plus permit acquisition. Unattributed is wrapper overhead minus every measured phase, where overhead excludes the compile on a compiled crate and is the whole wrapper time on a hit. Events written by wrappers before schema 17 report zero startup, dep-info and wait time.

In the trace output each crate slice carries these numbers in its `args`. It nests one `X` slice per phase on the same lane, in this order: `startup`, `key` (with `dep-info` as its child), `lookup`, `wait`, `compile` on compiled crates, then `restore` or `store`. Phase offsets accumulate from the crate slice's start in that order; the wrapper records durations, not start times, so a phase sits where it lands in the sum. The gap after the last phase is the unattributed remainder. Durations are whole milliseconds, so a phase under 1 ms has no slice. A remote transfer that has both a start and a finish follows the crate slices as an async `b`/`e` pair with category `kache.transfer`.

`--redact` applies to every format. Build roots, store paths, the cache directory and your home directory are replaced wherever they appear, including inside messages such as store errors. The `telemetry/sessions.jsonl` line is written before redaction, so its root hash comes from the real root. The line holds no cache keys. Empty fields stay empty. A C or C++ row can also carry `object_output`, the path named with `-o`. A build-script row carries `package`.

## `kache telemetry`

```bash
kache telemetry write ./cache-otlp
kache telemetry write ./cache-otlp --scenario bench-firefox --phase warm
```

Writes `metrics.otlp.json` and `schema_version` for Kartero. Metric names are `kache.cache.*` (scope `kache.cache`), never `kache.bench.*`. `--scenario` must match `kache.bench.project`. `--phase` is `cold`, `warm-same-tree`, `warm`, or `pull` so dumps from the same scenario do not collide. The rustc wrapper does not write these files.

The payload also carries this host's local store: registered blob bytes (`kache.cache.store.physical_size`), index and WAL size, and a rowid high-water mark per table (`kache.cache.index.*`; it is not a row count). `kache.cache.store.size` counts logical entry bytes; GC compares the physical blob figure with `kache.cache.store.max`. Last-run GC gauges include duration, pinned and unreclaimable entries, bytes held by target directories, failed evictions, stale WAL snapshot failures, and recently accessed entries skipped before reading their metadata. The read-only index probe has a 25 ms lock timeout; unavailable figures are omitted.

## `kache explain`

With `[cache] explain_miss = true`, `kache explain <crate>` names compiler-reported environment variables that differ from the prior build of that unit. It compares normalized value hashes, so the log keeps variable names without their values. Older events without these hashes cannot supply the hints. The same hints appear in the JSON report.

`kache why-miss` is the same command under its earlier name.

### One crate

```bash
kache explain serde
kache --json explain serde
```

Explains the latest recorded miss using the event log and stored entries. Store failures and rejected entries take precedence over key comparisons. Repeated misses under the same key in older logs retain an unknown cause when those logs cannot explain what happened.

The terminal report shows the last miss, its diagnosis, comparison with another build tree and dependency cascade when available, followed by stored entries and recent events.

When the crate's newest compile was not cached, such as an edit rebuild that rustc compiled incrementally or a compile kache declined to store, `explain` reports that compile and why it was not cached instead of the older miss. JSON carries it in `latest_uncached_compile`, which is `null` otherwise.

Terminal and JSON output share the diagnosis and dependency analysis. For a recorded miss, JSON includes `dependency_chain` with changed dependencies, endpoints, and any traversal limit. An unresolved endpoint is not a confirmed cause. `dependency_recording_missing` indicates when setting `explain_miss = true` under `[cache]` and rebuilding can provide the missing dependency evidence.

The first build in a second clone or worktree has no earlier build of the crate in its own tree. In that case `explain` compares the miss with the most recent build of the same compilation unit in another build tree, usually the other checkout. The output names that tree and gives one of these verdicts:

- The crate's own input groups differ.
- Only its dependencies differ.
- Both trees computed the same key. No key input differs, so the key is not why the crate missed.

It then walks the dependency cascade through the builds the other tree used. It names the crate that changed and shows the crates above it on the `via:` path. A root whose key matches the other tree while its artifact differs is reported as not reproducible across build trees (JSON kind `path_only`). JSON carries the comparison in `checkout_comparison` and the other tree in `dependency_chain.baseline_root`.

Build trees are matched by Cargo's unit id. It is the same for a workspace member in every checkout of a project, and for a registry crate built the same way in unrelated projects. Kache records it only with `[cache] explain_miss` on, so both builds need it. A build of the crate in the same tree is always preferred.

> A crate that depends on a path crate outside the workspace root, or is built with `RUSTFLAGS` that contain the checkout path, gets a different unit id in each checkout. It has no comparison.

## `kache config`

```bash
kache config
kache config path
kache config list --json
kache config get cache.cache_executables
kache config set --project cache.cache_executables false
kache config unset --project cache.cache_executables
```

Without a subcommand, lists the selected file's values. The subcommands read or edit the selected TOML file without starting a daemon. `get` and `list` show explicit file values, excluding environment overrides, host settings and defaults. A missing key makes `get` or `unset` fail.

Each subcommand accepts `--project`, `--global`, or `--file PATH`. Without one, it uses Kache's normal config-file selection. `--project` selects the nearest existing `.kache.toml`, or creates it in the current directory when setting a value. `--global` selects the user config and ignores `KACHE_CONFIG` and project files. `--file` selects an explicit path. These selectors cannot be combined.

`set` validates known keys and their TOML types. Boolean, number and array values use TOML syntax; strings such as `50GiB` can be unquoted. Workspace declarations and entire tables are edited directly in TOML. Edits preserve comments and other keys, follow existing file symlinks, and replace the file atomically under a writer lock. Invalid TOML is refused. All subcommands support `--json`. See [Configuration](/docs/getting-started/configuration).

## `kache completions`

`kache init` installs and refreshes completions for Bash, Zsh, and Fish on Unix. This command prints a script for manual setup:

```bash
kache completions zsh > ~/.zfunc/_kache
kache completions bash > ~/.local/share/bash-completion/completions/kache
kache completions fish > ~/.config/fish/completions/kache.fish
```

Supported shells are Bash, Elvish, Fish, PowerShell, and Zsh.

## Volume shards

With `[cache.volumes]`, `stats` and `report` sum bytes across stores and count unique cache keys. `list` and `explain` show each entry's store directories. `doctor` reports a shard with no index without creating it. `doctor --verify` checks every copy, shards included, and stops with an error at a shard that has no index. See [Volume shards](/docs/getting-started/configuration#volume-shards).
