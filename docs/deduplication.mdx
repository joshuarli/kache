---
title: Deduplication
description: How Kache shares output bytes and restores them safely
---

Kache saves disk in two independent places: inside the store and between the store and build trees.

## Content-addressed blobs

Each output blob is named by its BLAKE3 content hash:

```text
<cache-dir>/store/blobs/ab/abcdef...
```

Entries refer to blobs through metadata and the SQLite index. Identical bytes share one blob even when they came from different cache keys. Garbage collection removes a blob only after no entry needs it.

## Restore methods

Kache uses the first of these methods that applies to an artifact:

1. copy-on-write clone on APFS, ReFS, btrfs, or reflink-capable XFS
2. on Unix, a hardlink to the blob for an immutable Rust output such as an `.rlib`, and on Linux also for proc-macro libraries and build-script binaries. Only one target directory may link a given blob; later restores copy it.
3. byte copy

C/C++ objects, Rust metadata (`.rmeta`), and the files a cached build script wrote are cloned onto their own inode or copied, never hardlinked. Metadata restores use the destination directory's creation permissions, including the current umask and inherited ACLs, and stay non-executable. `[cache] shared_hardlink_restores = true` lets every target directory hardlink an eligible blob; use it only for target directories nothing reads after the job, such as a CI job's.

Other executable and loadable outputs use clone or copy, never the hardlink fallback, because signing, stripping, or another consumer may modify them. On Linux, proc-macro libraries and build-script binaries share the blob's inode when the blob is read-only and executable, since nothing rewrites them after a restore. A blob without every execute bit is copied. On volumes without copy-on-write cloning, restores copy.

Restored reflinks and copies are writable by their owner, so a later compiler invocation can overwrite them after you remove the Kache wrapper. Immutable Rust reflinks gain owner write access while retaining their other permissions and leaving the cache blob read-only. A hardlink carrier shares permissions with the blob and stays read-only; rebuilding those outputs without Kache can require removing them first.

Upgrading does not rewrite outputs Cargo already considers fresh. If older read-only metadata blocks `cargo fix`, [rebuild the affected package's outputs](/docs/getting-started/troubleshooting#cargo-fix-cannot-write-old-metadata). The shared artifact cache can stay in place.

Reflinks have independent inodes. A later write copies changed blocks instead of modifying the store blob.

## Reported sizes

In `kache stats`, Cache and Store show registered blob bytes; Limit is the
registered blob budget. Dedup shows logical output bytes and the percentage
saved. If blob inventory is unavailable, the size is labeled as logical.
Registered bytes describe the cache's index, rather than all space allocated
on disk or the additional blocks occupied by restored worktrees.

When target directories share blocks with the store, through clones or
hardlinks, or filesystem snapshots still hold some, `kache stats` adds an
`On disk` row: the bytes only the store holds, the part also cloned into
`target/` directories, and the part only snapshots hold. Clone detection is
reliable on macOS and depends on the filesystem on Linux.

Run `cargo clean` in a project to remove its build outputs.

## `dup` build events

A `dup` event means the cache key missed, the compiler ran, and all resulting blobs were already present. It is not a restore, and it is separate from the `Dedup` metric. Repeated dups can expose noisy or over-specific key inputs.
