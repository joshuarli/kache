Kache resolves settings in this order:

1. environment variable
2. config file
3. [host config](#host-config)
4. built-in default

Some settings exist only as environment variables, among them `KACHE_DISABLED`, `KACHE_CONFIG`, `KACHE_HOST_CONFIG`, `KACHE_SOCKET_PATH`, `KACHE_TRUST_DOMAIN`, and the logging and progress controls. Where the tables below list one, its TOML key is `none`.

## Config file

Open the editor:

```bash
kache config
```

For scripts, use the file commands:

```bash
kache config path
kache config list --json
kache config set --project cache.cache_executables false
kache config get --project cache.cache_executables
kache config unset --project cache.cache_executables
kache config set --global cache.local_max_size 50GiB
```

`get` and `list` report values written in the selected file, before environment overrides, host settings or defaults. `get` and `unset` fail when the key is absent. `set` accepts known keys with matching TOML types; quote array values for the shell, for example `kache config set paths.base_dirs '["/work", "/sources"]'`. Workspace declarations and entire tables are edited directly in TOML.

`--project` uses the nearest existing `.kache.toml`, or creates one in the current directory on `set`. `--global` chooses the user config even when `KACHE_CONFIG` or a project file exists. `--file PATH` selects another file. These selectors are mutually exclusive and follow the subcommand. Without a selector, the commands use the same file selection as the editor. All five subcommands support `--json`.

The commands change the file only. A daemon setting takes effect when the daemon next loads it; restart the daemon when you need a running instance to use the changed value.

Or edit TOML directly. Kache chooses the first file in this order:

1. `KACHE_CONFIG`
2. the nearest `.kache.toml`, walking up from the current directory
3. `$XDG_CONFIG_HOME/kache/config.toml` or `~/.config/kache/config.toml`

Kache reads only that one file, plus the [host config](#host-config); a `.kache.toml` does not merge with your user config.

Each process walks up from its own current directory. Cargo compiles packages under the workspace root from the workspace root, but compiles registry and git dependencies, and runs their build scripts, from each package's source directory under `$CARGO_HOME`, so those compiles do not see your project's `.kache.toml`. A daemon that a build starts resolves its file from the directory of the compile that started it, which can be a dependency's source directory. To apply a setting to every compile and to the daemon, put it in your user config or the host config, or point `KACHE_CONFIG` at the file.

If the chosen file is not valid TOML, or a key has the wrong type, Kache ignores the whole file, and the host config with it, and runs on environment variables and defaults without a warning. Size keys (`local_max_size`, `event_log_max_size`) take quoted strings such as `"50GiB"`.

The editor covers common fields and updates changed keys while keeping comments and other settings. It asks before its first save to an existing file and refuses a file it cannot read or parse. The file subcommands also preserve comments and unrelated settings; `unset` can remove an unknown key.

```toml title="~/.config/kache/config.toml"
[cache]
cache_executables = true
local_max_size = "50GiB"
```

### Host config

A machine owner can set keys for every build on the machine in `/etc/kache/config.toml`. Kache merges it with the chosen file key by key: a key the chosen file sets wins, and a key it leaves unset comes from the host file. Environment variables still win over both.

The host file reaches CI jobs too. A host file like this applies to every job on the runner:

```toml title="/etc/kache/config.toml"
[cache]
local_max_size = "200GiB"
```

- `[cache.volumes]` is replaced whole. If the chosen file declares one, none of the host file's keys for it apply.
- The host file never contributes `[workspace]` declarations. Those belong to a project's `.kache.toml`.
- The host file cannot set `ignore_env`. Kache ignores it with a warning, so the host file can never turn environment overrides off. Only the chosen file can; see [Pin file-backed settings](#pin-file-backed-settings).
- A host file that cannot be read or parsed is ignored with a warning. `kache doctor` reports it, and lists each host key with whatever overrides it.
- `KACHE_HOST_CONFIG` reads another path instead. An empty value turns the host layer off.
- `kache config` edits the chosen file, never the host file.

The names `cache.cache_dir`, `cache.max_size`, `cache.source`, and
`cache.fingerprint` are internal records — env-override tracking, host-key
sources, and the config-file snapshot compared when the daemon and a client
disagree — not settings you can set.

## GC and shared build outputs

`cache.local_max_size` measures blob bytes registered in Kache's store. A Cargo target directory can hardlink or block-clone those blobs. In that case the store name and the build output refer to the same disk blocks.

By default, GC keeps an entry when removing its last store name would reclaim zero bytes. This preserves a usable cache hit. It also means the registered store size can remain above `local_max_size` until the target output is removed. `kache gc` reports these entries as unreclaimable, with the bytes they hold, and separates store bytes removed from disk bytes reclaimed.

A size-driven sweep leaves those held bytes out of its budget. Before it removes anything, it finds the entries whose last blob a build output still holds, and it evicts until the rest of the store is back under the target. A store whose registered size is mostly held by target directories is therefore not evicted further: removing other entries would lose cache hits without bringing the held bytes down.

Automatic eviction has one trigger: a sweep starts when the store is above 110% of `local_max_size` and evicts down to 90%. Three things can ask for one: a build that has just stored an entry (checked at most every 5 minutes), the daemon after an upload, and the daemon's 6-hour sweep. `kache gc` evicts from 100%.

While a daemon is running, it does the sweeping. A build that finds the store over the trigger sends the daemon a hint and continues; it does not wait for the sweep, and it never starts a daemon for this. Hints that arrive during a sweep are dropped. With no daemon, or a daemon too old to accept the hint, the build starts a detached `kache gc`. That worker sweeps a second time two minutes later only if the first sweep had to skip entries a running build was using.

Every automatic sweep records the store size it ended at, whichever of the three started it. When an automatic sweep leaves the store over budget, the next automatic sweep waits 10 minutes. Each further sweep that ends over budget doubles the wait, up to 2 hours. The wait ends early when the store grows by more than 10% of `local_max_size`, and resets once a sweep brings the store back under budget. The wait applies to all three, so one sweep that cannot free enough holds the others back too. The 6-hour sweep still expires entries by `cache.gc_max_age_hours` and removes duplicates during a wait; only its size eviction is skipped. The state lives in `auto-gc-backoff.json` in the cache dir. `kache gc` ignores it.

`auto-gc-backoff.json` also keeps the bytes the last sweep found held by target directories. For 6 hours the trigger compares the store size minus those bytes with 110% of `local_max_size`, so a store over budget only on held bytes starts no sweep. Deleting a worktree frees what it held without changing the store size; after 6 hours the trigger uses the full size again, and the next sweep measures anew.

Automatic sweeps also keep entries imported in the last 6 hours, whether a build has used them yet or not. A CI job that stores entries and then runs several cargo commands keeps them for the whole job; without this, an eviction between two commands could drop what the next command needs. If those entries alone keep the store over budget, the sweep stops and backs off as described above. `kache gc` does not keep them.

A sweep pauses for 150 ms after every 50 ms of index writes, and after each removal that finds a build holding the index write lock, so the sweep does not hold up builds that are storing entries.

To reclaim the blocks, remove the retaining build output. Run `cargo clean` in the relevant project to remove its build outputs.

If enforcing the store namespace limit matters more than retaining hits, let GC evict shared entries:

```toml title="~/.config/kache/config.toml"
[cache]
gc_evict_shared = true
```

The equivalent environment setting is `KACHE_GC_EVICT_SHARED=1`. With this option, GC can drop an entry even though target files still hold all its blocks. The registered store size falls, but disk usage does not. A later build must compile or download that entry again. Explicit `purge` and repair operations remain unconditional regardless of this setting.

### Volume shards

Every GC driver sweeps each `[cache.volumes]` shard as well as the main store: `kache gc`, the daemon's 6-hour sweep, its sweep after an upload or a build's hint, and the detached auto-GC worker. Each shard is swept like the main store, with the same age, duplicate, and size passes.

Each shard has its own budget. An explicit `local_max_size` or `KACHE_MAX_SIZE` applies to each shard as it is. Without one, a shard's budget is 5% of the filesystem that holds it, floored at 5GiB and capped at 100GiB, the same rule as the main store.

A shard keeps its own `gc.lock`, `auto-gc-backoff.json`, `gc_stats.json` and `savings.json` in its store dir, so its trigger, backoff and held bytes do not mix with the main store's. `kache gc` prints one line per shard after the main store's.

GC skips a shard whose store dir has no `index.db`: a missing directory, an unmounted volume, or a shard no build has written to yet. It never creates a shard directory. A shard that fails to open or sweep is logged, and GC carries on with the others and the main store.

`kache stats` and `kache stats --full` include every configured store. Entry counts count each cache key once; stored bytes count every copy across stores. JSON includes per-store paths, sizes, budgets and errors. The `stats --json` filesystem `disk` and index measurements still describe the main store; use `stores` for shard measurements.

`kache list` and `kache explain <crate>` show the stores that hold each entry. `kache doctor` checks shard availability and accounting. Its link-layout probe resolves the intermediate directory from Cargo configuration and environment variables, falling back to the target directory. It probes that directory, or its nearest existing ancestor, using the shard mapped to the probe path. Configuration that Kache cannot resolve produces a diagnostic instead of a link probe. `doctor --verify` checks every stored copy; `--repair` also repairs shards. Missing shards are reported without creating their directories.

`kache gc --json`, `kache gc --stale-schema` and emptying the cache with `kache clean --cache` still cover only the main store.

### Daemon index maintenance

The daemon looks after `index.db` on its own. It checks 60 seconds after it starts, every 5 minutes after that, and once at shutdown. Each check runs two steps in order: it heals the blob index, then compacts the file. Both steps hold the index write lock while they work, so both wait for a quiet machine. A machine is quiet when no compile holds a scheduler slot, and the daemon has received no build request for 60 seconds. Stats polling does not count as a build request. Neither step overlaps a GC sweep.

`kache doctor --repair` does the same work on demand.

#### Blob index heal

The index keeps two tables about blobs: one row per blob with its size and a reference count, and one row per entry and blob it uses. Both are derived from the entries themselves. They can drift apart: a blob row keeps a reference count that no entry accounts for. Such a blob still counts toward `max_size`, but eviction only removes blobs through entries, so GC cannot free it. A store with enough of them stays over its budget and keeps sweeping without getting under it.

Every check compares the two tables with one read-only query. When they disagree and the machine is quiet, the daemon rebuilds both tables from the `meta.json` of every committed entry, in one transaction. Blob files that no row references after that are deleted once they are an hour old, the same grace GC uses, so a store in the middle of a write is not disturbed. The compaction step that follows returns the freed pages to the disk.

The heal has no fallback for a machine that is never quiet. It reads every entry's metadata under the write lock, so its duration grows with the store. Drift costs disk space, never a wrong cache hit. At shutdown it runs only when the store has at most 25,000 entries. If another process is using the index when it starts, it stops at once and a later check retries.

The rebuild refuses to run if it cannot trust an entry: a `meta.json` that is missing or does not parse, or a blob that is missing or has the wrong size. It then changes nothing, logs one warning that names the entry, and waits 6 hours before it tries again. The wait is kept across daemon restarts, in `blob-heal.json` in the cache dir. To fix it, run `kache doctor --repair` when no build is running: it removes the corrupt entry and rebuilds the blob index.

#### Index compaction

Deleting rows from `index.db` frees pages inside the file but does not shrink it. After a large prune or a schema migration, most of the file can be free pages. The daemon compacts the index with a SQLite `VACUUM` once free pages reach 64 MiB and a quarter of the file.

A `VACUUM` blocks other index users while it runs, so the daemon runs one only in these cases:

- On a quiet machine, when the live part of the index is at most 8 GiB. If anything else is using the index at that moment, the attempt stops at once and a later check retries.
- At daemon shutdown, under the same permit rule, when the live part of the index is at most 1 GiB.
- On a machine that is never quiet: after the index has stayed over the threshold for 6 hours, and only when the live part is at most 1 GiB. Index reads continue during the rewrite. Index writes wait for it, which at that size is a few seconds, inside the wrappers' normal index timeout. The 6 hours are counted across daemon restarts, in `index-compact.json` in the cache dir.

Compaction needs free disk of about twice the live index size, not the file size: a 45 GB index with 1 GB live needs about 2 GB. Without that room the attempt is skipped and retried later. The free pages stay reusable in the meantime, so a skipped compaction costs disk space only.

A live index above 8 GiB is never compacted automatically, because the rewrite would hold the index for too long. The daemon logs that it skipped it; run `kache doctor --repair` when no build is running.

### Free-space recovery

Set `cache.auto_recover_min_free_bytes` to the minimum free space on the store's volume. Below that floor, Kache evicts eligible cache entries. Set it to `0` to disable recovery.

```toml title=".kache.toml"
[cache]
exclude = ["vendor/problematic/**"]
bypass_crates = ["generated_bindings"]
bypass_argv = ["--cfg", "uncacheable_mode"]
bypass_env = ["SPECIAL_BUILD=1"]
```

## Cache-key controls

| Environment | TOML key | Default | Purpose |
| --- | --- | --- | --- |
| `KACHE_KEY_SALT` | `cache.key_salt` | none | Opaque value folded into every key |
| `KACHE_BASE_DIR` | none | none | One extra path prefix normalized as `<BASE_DIR>` |
| none | `paths.base_dirs` | `[]` | Additional absolute prefixes with distinct stable sentinels |
| `KACHE_PATH_ONLY_ENV_VARS` | `cache.path_only_env_vars` | `[]` | Path locator variables eligible for safe normalization |
| `KACHE_KEY_ENV_VARS` | `cache.key_env_vars` | `[]` | Environment read by proc macros but not reported by rustc |
| `KACHE_VERIFY_RESTORES` | none | `off` | Re-hash `sampled` or `always` before restoring |
| `KACHE_VERIFY` | none | `off` | Recompile each rustc cache hit and compare it to the restored files |

Use `KACHE_VERIFY` to check a cache-key change. Set it to `1` or `true` to recompile every rustc cache hit into a staging directory and diff those artifacts against the files just restored. Leave it unset (or `0` / `false`) in ordinary builds: each hit pays a full compile. There is no `kache build` command for this.

Path and debug-info bytes that differ only as embedded absolute paths are reported as `path-debug` and do not fail the build. Remaining byte differences are `content`. In both cases the restored files stay in place so the build continues; the wrapper records the class on the hit event as `verify_compare` (and in the log when logging is on).

`KACHE_VERIFY_RESTORES` only re-hashes stored blobs before restore. It does not recompile.

Use a key salt when an unobserved toolchain component changes output:

```toml
[cache]
key_salt = "sysroot-2026-08"
```

Keep `paths.base_dirs` narrow. Normalizing unrelated roots to stable sentinels can make different inputs appear equal.

`path_only_env_vars` widens the built-in `OUT_DIR` rule to other variables
whose value only locates a generated file. A plain `VAR` entry still has to
pass Kache's checks: some source must show `env!("VAR")` (or `option_env!`)
inside an `include!`, `include_str!` or `include_bytes!` argument, and no
source may read the value anywhere else. Kache also needs dep-info to list a
file under the value, and it reads the proof only from `.rs` sources. When a
listed variable is not normalized, `KACHE_LOG=trace` prints which of those
conditions failed next to the `env_dep:` line.

A crate that includes generated code through another crate's macro, such as
`tonic::include_proto!` or `lalrpop_mod!`, never spells `env!("OUT_DIR")`
itself, so the check finds no proof and the absolute path stays in the key.
That crate then rebuilds in every checkout. Assert it per crate, using rustc's
crate name (underscores):

```toml
[cache]
path_only_env_vars = ["my_proto_crate:OUT_DIR"]
```

A `crate:VAR` entry skips the source checks for that crate and variable only,
so use it when you have read the crate and know it never bakes the value into
its artifacts. `CARGO_MANIFEST_DIR` is never accepted, in either form: rustc
embeds it in crate metadata, and every crate's sources live under it, so the
checks above would pass for a value that does change the artifact. Kache warns
when a list names it and ignores the entry.

Build scripts can also share runs when a linker wrapper lives in each
checkout. Set `KACHE_BASE_DIR` to the checkout root and opt the tool variable
into normalization:

```toml
[cache]
path_only_env_vars = ["RUSTC_LINKER"]
```

For build-script runs, plain `RUSTC_LINKER`, `RUSTC`, and `RUSTDOC` entries
normalize a tool path under `KACHE_BASE_DIR` and hash the tool file's contents.
Different tool bytes still produce different keys. Use this only when moving
the tool between identical checkouts does not change its behavior. A wrapper
that reads other files must declare those inputs with `cargo:rerun-if-changed`.
Other variables and crate-scoped entries keep their existing behavior.

Registry crates that bake an empty `OUT_DIR` need no entry. On Unix, Kache
compiles a registry proc macro whose `OUT_DIR` is empty, or a registry lib that
only proc macros link, against `<cache>/out-dirs/v1/d/<pkg>-<hash>/out`: an
empty directory with mode 0555 at the same path in every checkout. A lib is
shared only once a build on this machine has shown that nothing but proc macros
links it, so the first checkout still rebuilds it. A `crate:VAR` entry for
`OUT_DIR`, or for a variable whose value is under it, keeps that crate on its
own `OUT_DIR`. A macro that writes debug output into the shared directory fails
with a hint: run `cargo clean -p <crate>` and rebuild. The hint comes from rustc's error output, so a compile
that Kache passes straight to rustc fails with rustc's error alone. That covers
a `bypass_*` or `exclude` match and an incremental compile.

`key_env_vars` accepts exact names and trailing-star prefix patterns:

```toml
[cache]
key_env_vars = ["BOLTFFI_*"]
```

Values are hashed exactly and are not written to event logs. A value that changes on every job, such as a job ID, gives every job its own keys.

## Hidden compile-time inputs

Some macros read files that rustc does not report. If the package's build script already declares them with `cargo:rerun-if-changed`, Kache keys them without a declaration of its own (see [Build scripts](/docs/how-it-works/build-scripts#declared-inputs-in-the-rust-key)). Otherwise put `kache.toml` without a leading dot next to the crate manifest:

```toml title="crates/db/kache.toml"
extra_inputs = [
  ".sqlx/**/*.json",
  "migrations/**/*.sql",
]
```

Matches are relative to that crate. Kache folds their paths and contents into its key and adds bounded watches to Cargo dep-info. Invalid or unreadable declarations fail closed.

For a workspace-root input used by a provider package and its direct consumers:

```toml title=".kache.toml"
[[workspace.extra_inputs]]
crates = ["query-macros"]
inputs = [".sqlx/**/*.json"]
propagate_to_dependents = true
```

Workspace rules are accepted only from the `.kache.toml` beside the active Cargo workspace manifest. After adding a declaration to a target Cargo already considers fresh, rebuild that package once.

## Telemetry

Kache does not push metrics to a collector. It writes OTLP JSON files that Kartero imports from CI artifacts, the same way it imports nightly bench results.

The two metric families stay separate:

- `kache.bench.*`: one-shot bench gauges (duration, speedup, verdict) from `kache-scenario`
- `kache.cache.*`: cache counters (store size and GC) from `kache telemetry write`

```bash
kache telemetry write ./cache-otlp --scenario bench-firefox --phase warm
```

That writes `metrics.otlp.json` and `schema_version` in the directory. `--scenario` must match `kache.bench.project`. `--phase` distinguishes cold from warm: the bench stops the daemon between phases, so counters are per daemon lifetime. The rustc wrapper does not write these files.

### Machine telemetry

On a host where several jobs share one cache, the payload reports `kache.cache.store.physical_size`: registered blob bytes, the figure GC compares with `kache.cache.store.max`. `kache.cache.store.size` is the sum of logical entry sizes and may differ. `kache.cache.store.unowned.size` is the part of the physical size held by blobs no entry maps to, which GC cannot free. `kache.cache.store.refcount_drift` counts the blobs whose reference count disagrees with the entries mapped to them, unowned ones included. Both are zero on a healthy store and return to zero after a [blob index heal](#blob-index-heal). It also reports `kache.cache.index.size` (`index.db` plus `-wal`), `kache.cache.index.wal.size`, `kache.cache.index.free.size` (the space `index.db` holds in free pages, which compaction returns to the disk), and `kache.cache.index.rowid_high_water` per table. Last-run GC gauges include duration, pinned and unreclaimable entries, bytes held by target directories (`kache.cache.gc.last_run.bytes_held`), failed evictions, stale WAL snapshot failures, and recently accessed entries skipped before reading their metadata. The shipper adds host identity. The index probe is read-only with a 25 ms lock timeout and omits unavailable figures. `kache stats --json` carries the index figures and GC summary as `index_bytes`, `index_wal_bytes`, `index_rowid_high_water` and `gc`.

`rowid_high_water` reports the largest rowid in each table. Tables written with `INSERT OR REPLACE` (`input_predictions`, `eviction_tombstones`) allocate new rowids on replacement, so this value can grow without adding rows. `file_hashes` has no rowid once GC has rebuilt it as a `WITHOUT ROWID` table, and then drops out of this series. C/C++ memos keep their IDs on update; their high-water value does not count refreshes. Use `kache.cache.index.size` to measure index bytes.

To keep per-build numbers at machine level, add `--record` to `kache stats --full`:

```bash
kache stats --format github --since 24h --record
```

After rendering the report as usual, it appends one JSON line to `telemetry/sessions.jsonl` in the cache dir. The line holds the report's summary and timing breakdown (hit overhead, key, dep-info pre-pass, restore, wait, prediction mismatches), plus load average, CPUs and index size at that moment. Use it at the end of a CI job: the report reads the runtime dir, which the job's cleanup deletes. The root is recorded as a hash, never as a path.

To record every report on a host without passing the flag, set `KACHE_RECORD_SESSIONS=1` or `[cache] record_sessions = true`. Recording is off by default: without the setting or `--record`, `kache stats --full` writes nothing.

Every GC driver (the daemon's sweep and its eviction after an upload, the auto-GC worker, and `kache gc`) records its run in `gc_stats.json`. With `record_sessions` on, each run also appends a version 2 line to `telemetry/gc-runs.jsonl` with the driver, outcome, duration, lock failures, stale WAL snapshot failures, and recently accessed entries skipped before metadata reads. `gc_stats.json` keeps only the latest run; the history is what a backend adds up. The bytes each run frees are also added to `savings.json`, the lifetime totals `kache stats` shows. Skip counts are attempts across policy passes, not unique entries.

`kache telemetry write` reads index rows and files locally; it sends nothing over the network.

## Daemon, events, and diagnostics

| Environment | TOML key | Default | Purpose |
| --- | --- | --- | --- |
| `KACHE_TRUST_DAEMON_EXECUTION` | `cache.trust_daemon_execution` | `false` | Both peers must opt in. Allows a trusted daemon pipeline under Linux Seccomp/NoNewPrivs or macOS sandboxes. Compiler children and artifact restoration run in the client; input discovery and other pipeline accesses retain the daemon's restrictions. See [Process restrictions](/docs/how-it-works/architecture#process-restrictions). |
| `KACHE_PROGRESS` | none | off | `hits` or `verbose` compiler progress |
| `KACHE_LOG` | none | CLI: `kache=warn`; wrapper: off | Stderr log filter |
| `KACHE_LOG_FILE` | none | CLI/daemon: `kache=info`; wrapper: off | File log filter and wrapper opt-in. The file is `~/Library/Logs/kache/kache.log` on macOS and `kache.log` in the default store directory elsewhere, even when `KACHE_CACHE_DIR` or `cache.local_store` moves the store. A process that starts while it is over 5 MiB truncates it |
| `KACHE_EVENT_ROOT` | none | detected | Root attached to events for report filtering |
| `KACHE_PAGER` | none | platform pager | Pager command for `kache list` |
| `KACHE_MAX_DIAGNOSTICS_BYTES` | none | unset | Cap, in bytes, on the compiler diagnostics stored with an entry. Unset stores them in full, so a hit replays exactly what the compile printed. Above the cap they are truncated with a marker |

Compiler event writes wait up to 5 ms to acquire the log lock, then omit the
record if it is still busy. This affects diagnostics, not compiler output or
cache validation. Rotation is deferred when the log or savings ledger is busy.
The lock budget does not bound filesystem I/O after acquisition.

Heartbeat ETA and miss explanations inspect at most 256 KiB of recent complete
event records and parse them after releasing the lock. An unavailable log or
missing recent history leaves the estimate or explanation empty. Compiler exit
allows 50 ms for the heartbeat to stop, then continues without joining a stalled
diagnostic thread.

## Pin file-backed settings

Set `cache.ignore_env` in a controlled project config to ignore environment overrides for settings that also exist in TOML:

```toml
[cache]
ignore_env = true
```

It does not suppress `KACHE_DISABLED`, `KACHE_CONFIG`, `KACHE_HOST_CONFIG`, `KACHE_SOCKET_PATH`, `KACHE_TRUST_DOMAIN`, logging, progress, or other environment-only controls. It does suppress file-backed settings that also have a TOML key, so a controlled project config pins those values. Kache warns when it ignores a set variable.

The daemon reads configuration at startup and watches the active config file and the host config. When either changes, the daemon drains and exits, and the next start loads the new settings. Other settings come from the environment the daemon started with. An installed service uses its service definition, not your current shell. See [Updates and config changes](/docs/daemon/lifecycle#updates-and-config-changes).

### Shared empty OUT_DIRs across stores

The default alias path includes the local store path. If jobs use different store paths, a proc macro that embeds its alias path produces different bytes and changes its dependents' cache keys. Give those jobs one absolute alias root instead:

```toml
[cache]
out_dir_alias_root = "/var/lib/kache-out-dirs"
```

Set `KACHE_OUT_DIR_ALIAS_ROOT` to override the file. Each host needs that same canonical path, writable by the build user; Kache creates private parents and empty read-only aliases beneath it. The setting applies on Unix, where OUT_DIR aliasing is supported.

When switching roots, clean existing Cargo targets so proc macros rebuild with the new path. Keep old alias directories while any artifacts may still reference them. Kache does not collect alias directories or the consumer evidence and deny markers stored with them. A macro that writes debug output fails with a hint naming the packages to clean, as described above.
