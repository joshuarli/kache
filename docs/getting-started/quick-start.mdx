Build one committed revision in two temporary worktrees. Each gets a fresh target directory, while Kache shares compatible cached outputs between them. Your existing checkout and build outputs stay in place.

## Enable Kache

[Install Kache](/docs/getting-started/installation), then run:

```bash
kache init
kache doctor
```

`kache init` configures Cargo's Rust wrapper and makes sure the background daemon is running. On Unix it also sets `HOST_CC` and `HOST_CXX` when unset, so Kache caches the C and C++ that build scripts compile, and offers Cargo and compiler shims with a `PATH` line for your zsh, bash or fish startup file and [test pacing](/docs/getting-started/configuration#test-runner). It also offers a login service. It does not set `CC` or `CXX`. See [C and C++](/docs/getting-started/c-cpp) for native build setup.

`init` also installs tab completions for Zsh, Bash, or Fish. Open a new terminal to load them. Use `--no-shell` to leave shell setup alone.

`doctor` checks the wrapper configuration, conflicting wrappers, cache configuration, daemon access, and Cargo and compiler shims. Resolve any setup issues it reports before continuing.

## Build in two worktrees

Use Bash, Zsh, or Git Bash at the root of a Rust repository with a committed `Cargo.toml` and `Cargo.lock`. The example builds `HEAD`; uncommitted changes stay in your original checkout. Complete any project-specific setup, such as initializing submodules, in each new worktree.

Run these blocks in the same shell:

```bash
kache_trial="$(mktemp -d)"
git worktree add --detach "$kache_trial/first" HEAD
git worktree add --detach "$kache_trial/second" HEAD
```

Build once to make eligible outputs available in the cache:

```bash
(
  set -e
  cd "$kache_trial/first"
  CARGO_INCREMENTAL=0 cargo build --locked --target-dir "$PWD/target"
)
```

Cargo enables incremental compilation for workspace members in its `dev` profile by default, and Kache passes those units through uncached by design (see [Incremental builds](#incremental-builds)). Without `CARGO_INCREMENTAL=0` the workspace crates bypass the cache and the second tree has nothing to reuse.

Then build the same revision in the second worktree:

```bash
(
  set -e
  cd "$kache_trial/second"
  KACHE_PROGRESS=hits CARGO_INCREMENTAL=0 cargo build --locked --target-dir "$PWD/target"
  kache stats --full --root "$PWD"
)
```

The explicit target paths keep the two builds separate even if you normally use a shared target directory. Cargo must request outputs for the second tree, so that Kache can restore them. Running Cargo again with an already populated target may do no compiler work and produce no new Kache events.

## Read the result

Look for cache hits and restored bytes in the second tree's report. The first build may also have hits if the store already contains compatible results. Some compiler invocations pass through; check the report's Not cached section before expecting every unit to hit.

The report covers the second tree’s recorded events from the last 24 hours. Only completed, retained compiler events appear. See the [command reference](/docs/commands/reference#the-full-report) for the available windows.

The report's Time saved row is compile work avoided: the summed compile time of the entries that hit, not elapsed build time saved. This example demonstrates reuse; a speed comparison needs repeated measurements of the same workload. Rust hits also do not prove that C or C++ compilations were cached.

If the second build misses, run `kache explain <crate>` with a Rust crate name from the report. It uses that crate’s latest recorded miss in any tree. When the second worktree has no earlier build of the crate and both builds ran with `[cache] explain_miss` on, it compares with the first worktree’s build instead. Check the reported input changes and the [cache limits](/docs/how-it-works/limits).

## Save a report

```bash
kache stats --full --root "$kache_trial/second" --format markdown --output "$kache_trial/reuse.md"
```

Open `reuse.md` before sharing it: reports include local paths and crate names, and store inventory covers the whole cache. The command writes a local file; publication is a separate action.

Kache is built by [Kunobi](https://kunobi.ninja/). When sharing a result, link this walkthrough so someone else can reproduce it.

Keep the worktrees for further experiments, or remove them from your original repository when finished:

```bash
git worktree remove "$kache_trial/first"
git worktree remove "$kache_trial/second"
```

The report stays at `$kache_trial/reuse.md`. Git may refuse to remove a worktree with local changes; review those files before removing it.

## Setup options

```bash
kache init --dry-run     # print proposed changes only
kache init --no-service  # configure Cargo without a login service
kache init --no-shell    # leave shell startup files unchanged
kache init --yes         # accept defaults without prompts
```

Init shows its plan and asks once before applying it, with a separate confirmation if another Cargo wrapper is set. It backs up existing files. Open a new terminal to activate C/C++ caching and test pacing; for C/C++ you can instead run the activation command it prints. `--dry-run` (or `--check`) shows the planned changes without prompts or modifications.

After setup, keep using ordinary Cargo commands. Give concurrent worktrees separate target directories. Tools that build in temporary copies, such as cargo-mutants, need no extra setup; see [Mutation testing](/docs/getting-started/mutation-testing).

## Executables and incremental builds

Kache caches eligible Rust executables by default: binaries, test binaries and build scripts, which Cargo compiles as executables. Override the policy with `KACHE_CACHE_EXECUTABLES` or `cache.cache_executables`.

## Incremental builds

Cargo enables incremental compilation by default for workspace members and path dependencies in its `dev` profile. When Cargo enables it for a unit, Kache passes that compiler invocation through unchanged and leaves Cargo's incremental directory alone: the unit does not use Kache's artifact cache. Registry dependencies already build without incremental state, so they still hit.

That is a deliberate tradeoff:

- Keep Cargo's default (`CARGO_INCREMENTAL` unset) to reuse incremental state *within* one target directory: edit rebuilds are fast there, but workspace crates never enter Kache's cache and never reuse across worktrees.
- Set `CARGO_INCREMENTAL=0` (as the walkthrough above does) to let eligible workspace units use the artifact cache instead: cold builds fill the cache, and other worktrees restore from it, at the cost of slower edit rebuilds in the same directory.

Mixing the two in the same target directory is allowed but each mode only reuses its own state. Use one setting per target directory when comparing hits.

## Temporarily disable caching

```bash
KACHE_DISABLED=1 cargo build
```

This keeps the wrapper in place but passes compiler work through.
